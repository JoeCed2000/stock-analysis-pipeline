## 🔴 Blockers (must fix before accepted)

### B1 — Missing: Concurrency model / bounded execution
**Files:** spec-technique.md §2, spec-fonctionnelle.md §3
**Problem:** Pipeline 9 étapes + async jobs + batch processing — aucun modèle de concurrence documenté. Combien d'analyses simultanées ? Que se passe-t-il si 2 utilisateurs analysent AAPL en même temps ? Les background jobs sont-ils bornés (max concurrent workers) ? La spec-technique mentionne "async" mais ne définit pas le modèle d'exécution (asyncio tasks? ThreadPoolExecutor?).
**Risk:** Race condition sur le cache, OOM si batch + analyse simultanée, corruption d'état si 2 analyses du même ticker.
**Fix:** Ajouter § "Modèle de concurrence" dans spec-technique : nombre max de workers async, locking par ticker, file d'attente batch, stratégie de backpressure.

### B2 — Missing: Observabilité runtime (health check contenu)
**Files:** spec-technique.md §11, spec-fonctionnelle.md §7
**Problem:** GET /api/health retourne `{"status": "healthy", "uptime": N}` — mais qu'est-ce que "healthy" signifie exactement ? Vérifie-t-il les 6 API sources ? La mémoire disponible ? L'espace disque ? La spec actuelle ne définit pas les critères de health au-delà de "le process écoute sur le port".
**Risk:** Health check qui retourne 200 alors que 4/6 API sources sont down — faux positif. L'auto-recovery ne détecte pas les défaillances partielles.
**Fix:** Définir health check en 3 niveaux : liveness (process up), readiness (APIs sources accessibles), disk (espace > 100MB). Documenter le format exact de HealthResponse.

### B3 — Missing: API source failure cascade scenarios
**Files:** spec-fonctionnelle.md §2 (UC-001-ERR), spec-technique.md §5
**Problem:** AC-003 couvre "Seeking Alpha indisponible" mais pas les cascades : que se passe-t-il si yfinance ET Finnhub sont down simultanément ? Si SEC EDGAR timeout sur 3 tickers batch d'affilée ? La spec actuelle a un "seuil ≥ 3 sources" (BR-002) mais pas de stratégie documentée pour les scénarios multi-failures.
**Risk:** Analyse qui échoue silencieusement avec < 3 sources au lieu de prévenir l'utilisateur. Batch qui bloque sur un ticker problématique.
**Fix:** Ajouter AC-003b "Double API failure" : Given yfinance + Finnhub down, Then analyse retourne statut "degraded" avec avertissement ET poursuit avec 4 sources restantes. Ajouter timeout par ticker en mode batch (skip après 3 min).
